# Limitations & risks

## Pivot limits (official APIs; P1 is tested against a mock Graph API; live: polling intake, AI reply and echo on one tester account, 2026-10-30)
- **Development mode, testers only.** Until Meta Business Verification and App Review for Advanced Access (both need a registered business, not available yet), the Meta app runs in Development mode with Standard Access. Only Instagram professional accounts that have a role on the app (the owner's own account and pilot shops added as Instagram testers, with consent) can connect. Other shops' customers cannot be served over Instagram yet. Meta's webhook page says an unpublished app receives only dashboard test webhooks; the owner published the app (no business approval was asked for) and real delivery is still to be confirmed live.
- **24-hour messaging window.** Hepson may send an Instagram reply only within 24 hours of the customer's last inbound message. Outside it the agent sends nothing and the shop is notified. Longer human replies need Meta's Human Agent feature (approval comes later) and apply to humans only (D23).
- **Webhooks need public HTTPS.** Instagram, Telegram and the payment providers call Hepson, so the API must be reachable on a public HTTPS URL. Local development needs a tunnel; the owner's machine alone is not enough. Webhooks must be signature- or secret-checked and idempotent.
- **Old browser connector removed (D41).** Its code and tables are gone. Browser profiles it left under `$HEPSON_DATA_DIR/profiles/` hold Instagram session cookies: delete them by hand. Shop conversations it mirrored stay as history but can no longer be answered.
- **Per-shop credentials.** Shops must supply their own Instagram authorization, Telegram bot, Nova Poshta key and merchant accounts (Monobank, WayForPay). Losing the master key means every shop must reconnect (D28).
- **Webhooks from Meta do not arrive (open, 2026-10-30).** With a Live app on Unified login, a connected account, a tester sender and "Allow access to messages" on, real DMs were not delivered as webhooks. What was verified: the public URL, the `GET` handshake and signature path work; Meta's app-level subscription (`GET /<app id>/subscriptions`: object `instagram`, correct callback, active, field `messages`) and the account-level one (`GET /<ig id>/subscribed_apps`: `messages`) are registered; the token reads `/<ig id>/conversations`, which showed each test DM; the dashboard **Test** button reached the route (a `changes[]` envelope with entry id `0`, dropped as an unknown account). Not found: why Meta sends no event for real DMs. Before the "Allow access to messages" toggle was effective, the Conversations call failed with `(#200) The account owner has disabled access to Instagram Direct Messaging Outside of Instagram App`; webhooks were still absent after it succeeded. Untested ideas: sender or app access level (Standard Access), a different tester account, Meta's webhook debugger, Meta support. **Workaround:** `HEPSON_INSTAGRAM_POLL_SECONDS` polls the Conversations API (see D29); it delivered a message, an AI reply and the echo without duplicates. Polling is a safety net, not a replacement: one Graph call per shop per run, extra delay, only recent messages, and the assumption that Conversations message ids equal webhook `mid`s is unverified (running both paths could store a message twice).
- **Development runs on polling (decision 2026-10-30, D30).** Until Meta delivers real message webhooks, Instagram intake in development uses `HEPSON_INSTAGRAM_POLL_SECONDS` (code default 0 = off; the owner's machine sets 10). Webhook code stays enabled and signature-checked. Consequences: (1) reply delay is up to one poll interval plus LLM time; (2) cost is one Graph call per connected shop per interval, so it scales linearly with shops and will meet Meta's per-app rate limits well before webhooks would; (3) each call reads only the 10 most recently updated conversations and 25 messages each, so a burst or an outage longer than Meta's retained window can lose messages permanently; (4) there is no durable queue between a Graph response and agent dispatch, so a crash mid-batch is recovered only if the messages are still inside that window; (5) reads, reactions, deletes and other non-message events are never seen; (6) a transient Graph or network error delays delivery by one cycle (the cursor is retained, nothing is lost); (7) if webhooks later start working alongside polling, duplicates are possible because poll ids equal webhook `mid`s only by assumption. Acceptable for a single-shop pilot; not acceptable as the multi-shop production path. Revisit before onboarding a second shop (Meta support report with app and account ids, then switch polling to a 60-120 s safety net).
- **Webhook code fixes (2026-10-30, local tests).** Connect now requires an explicit successful subscription response before atomically saving the channel and token; failed reconnects preserve the previous connection, and disconnect cancels pending connection callbacks. Early delivery during subscription receives a retryable 503. Account selection checks pagination rather than assuming the first page contains every shared account. Polling starts at connection time, retries failed batches without advancing the cursor, includes messages at the cursor timestamp, and resets the cursor when switching accounts. Stale responses after a connection change cannot ingest messages or invalidate a replacement token. Handshake token comparison handles UTF-8 safely; request logs redact encoded OAuth and verify-token parameter names. These fixes do not establish why Meta sent no real POSTs in the earlier live test. A new real delivery still needs verification.
- **P1 specifics, unverified.** Endpoint shapes, permissions, error numbers and the echo `mid` equality are from documentation (D23, D29). Since 2026-10-30 the connect/API layer uses Unified login (D29): the `state` round trip, the `messages` payload shape, the Send API path with the system-user token and the window error subcodes were not checked against Meta. Meta requires the app to be owned by a business portfolio (no verification needed for Standard Access). An echo typed in the Instagram app is stored as a human message but does not pause the AI. An `uncertain` send is not reconciled with a later echo (possible duplicate human row). Webhook processing is synchronous in the request (fast for text; profile lookup runs after the ack). Internal ingestion or synchronous agent-dispatch failures return 503 after other events in the batch are processed, allowing Meta to retry; successful events dedupe on replay. Permanently invalid or unsupported events are acknowledged and logged without their contents. Media/attachments are stored as kind only (no URLs, no download). Reactions, read receipts, story replies and postbacks are ignored. One Instagram account per shop. Master key in an environment variable, not a KMS (D28).
- **Unverified platforms.** Nothing has run against Nova Poshta (P4 is tested only against a fake written from NP's API documentation), Monobank (P5 is tested only against a fake written from Monobank's acquiring documentation, 2026-11-01) or WayForPay. Telegram (P2): connect, one inbound text message and one reply ran live on a test bot (2026-10-31); disconnect, blocked-bot and revoked-token responses and media are tested against a documentation-based fake only. Meta: see P1 status. Fixtures written from documentation are not evidence of real behavior.
- **Policy guard is a heuristic (P3).** It catches periods ("14 днів", "1-2 days"), clock hours and a fixed list of returns/payment/free-delivery/opening-hours phrasings in uk/ru/en. A policy claim worded without numbers or listed words (for example "you can send it back") passes. Numbers are matched against all numbers in the returned policy texts, not by meaning. The prompt and `get_policy` are the primary control.
- **Nova Poshta specifics, unverified (P4).** Method names, parameters, response fields, the refused-key error shape, phone formats and the tracking status codes (delivered 9/10/11/106, refused 102/103, storage ended 105) come from NP's public documentation. TTNs are branch to branch, recipient pays delivery, one seat, the shop's set weight; COD uses `BackwardDeliveryData` money (no "контроль оплати"). Storage ended (105) moves the order to `returning` but does not count as a refusal; a member can record one by hand.
- **TTN creation has no idempotency key at NP.** When NP gives no usable answer to `InternetDocument.save`, the order stays `uncertain`: no retry, no cancel, the shop is notified, and a member must check the NP cabinet and press "no waybill, retry". There is no lookup of an existing waybill by order.
- **Monobank specifics, unverified (P5).** Paths, the `X-Token` header, the create body (`amount`, `ccy`, `merchantPaymInfo.reference/destination`, `validity`, `paymentType: debit`, `webHookUrl`), the status schema, the `x-sign` scheme (base64 DER ECDSA over SHA-256 of the raw body, key from `/api/merchant/pubkey` as base64 PEM) and 403 for a refused token come from Monobank's public documentation. Not confirmed: the API error body (Hepson keeps only a short `errCode`), the meaning of each status, rate limits, the `merchantPaymInfo` schema beyond those two fields, and whether a `failure` invoice can still be paid. Fiscal receipts (ПРРО, `basketOrder`) are not sent; a shop with an active ПРРО link may get its invoices refused. Only UAH.
- **Payment-link edge cases (P5).** Monobank has no idempotency key either, but an invoice whose create answer was lost is never shown to anyone, so the attempt is recorded `create_failed` and a member may create a new link (the orphan invoice expires on its own). A payment that arrives after the order was cancelled (deadline or a member) is not applied: the order stays cancelled and an escalation asks the shop to refund in the cabinet. An invoice still `processing` at the deadline gets one more hour. Without an https `HEPSON_PUBLIC_URL` there are no webhooks and payments are found by the status check every `HEPSON_PAYMENT_CHECK_MINUTES`. The reply guard's "paid" check is a phrase list (uk/ru/en); a payment claim worded otherwise passes, and the prompt stays the primary control. Bank transfers outside Monobank cannot be marked paid (no manual "mark paid", D24).
- **Catalog import and export (P8).** Google Sheets import needs the sheet shared by link (no Google sign-in), reads one tab per run, is capped at 2 MB of CSV, and has run only against a fake (the redirect to a googleusercontent host is assumed from public descriptions). There is no scheduled re-sync: every import is a manual run. No XLSX import. The Excel export was checked with LibreOffice, not Microsoft Excel; it has no styling, and its timestamps are Kyiv-time text, not Excel dates.
- **Plans and quotas (P7).** No billing: plans are limits the operator assigns by hand. The cap counts sent AI replies, not model cost: runs that escalate or fail after calling the model are free, so token spend is bounded only indirectly. There is no warning before the cap (only the notice at it), and the quota month is UTC, so in Kyiv it rolls over at 02:00 or 03:00 local time.
- **Customer notices (P6).** One attempt per order and event, no retry. A notice whose send outcome is unknown (`uncertain`, or a crash mid-send) is not resent, and the dashboard says so. Instagram's 24-hour window has usually closed by the time a parcel ships or arrives, and no message tag is used (Human Agent needs App Review), so Instagram customers mostly do not get `shipped`/`delivered`: the shop is told instead. Notices queued while the server was down for more than 24 h are skipped. Member cancels, payment timeouts, returns and refunds send no customer message. Tested only against fakes for Telegram, Instagram and the connector.
- **Checkout needs Nova Poshta.** A shop without a connected NP key gets no AI drafts: the lookups fail and the agent escalates. Delivery to an address (courier) and other carriers are not supported.
- **No Hepson billing and no refunds automation** until the FOP exists; refunds are always human (D24).
- **Personal data.** Customer messages are personal data (GDPR/Ukrainian law). Logs never contain message text, tokens or cookies. There is no automatic retention purge and no per-customer export/delete endpoint for shop conversations yet (the removed connector's 30-day purge covered only its own tables).
