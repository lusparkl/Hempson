# Decisions

## D1 (2026-10-28): reuse SQLite + Drizzle for Phase 2
Phase 1 already ships better-sqlite3 + Drizzle with a migration chain, `Store`, and test helpers. Reused instead of adding PostgreSQL: zero setup, deterministic in-memory tests, one migration chain. Trade-off: single-writer, single-node; fine for local/early SaaS. Revisit before real multi-instance deployment. Schema uses portable column types; keep SQLite-specific SQL out of services so a Drizzle dialect swap stays feasible.

## D2: `shops` is separate from `store_accounts`
`store_accounts` are Instagram connector accounts (Phase 1). `shops` is the tenant root. Linking (`store_accounts.shop_id`) is deferred to Feature 5 to avoid altering Phase 1 storage now.

## D3: shop validation
slug `^[a-z0-9]+(-[a-z0-9]+)*$`, 2-63 chars, unique; currency 3 uppercase letters (ISO 4217 shape, not checked against a list); language BCP 47-style tag; name trimmed 1-120. Defaults UAH / uk. Create and update inputs are strict (unknown keys such as `id` are rejected). IDs are random UUIDs generated server-side.

## D4: handoff files
`docs/AI_HANDOFF.md` is the single state record for Phase 1 and Phase 2 (the separate Phase 2 `HANDOFF.md` was merged into it on 2026-10-29).

## D5: repository is internal-only
`ShopRepository` has no authorization; Feature 2 must put membership checks in front of any HTTP use.

## D6 (Feature 2): own minimal auth, no auth library
Email + password with `node:crypto` scrypt (N=16384, r=8, p=1, per-user salt, NFKC-normalized, min 10 chars); no new dependency. Sessions are opaque random tokens `hsu_…` sent as `Authorization: Bearer`; only sha256 is stored; default TTL 30 days (`HEPSON_SESSION_TTL_DAYS`), revocable via logout. Chosen over a library/JWT to keep revocation trivial and the surface small. Trade-offs: no email verification, password reset, 2FA, or refresh rotation yet; bearer tokens (not cookies) so the future dashboard must hold the token and should add CSRF-safe cookie handling if it switches to cookies. Login throttle: 5 failures / 15 min per email, in memory (resets on restart, per-node).

## D7: credential separation
Connector API keys (`hep_…`, Phase 1) and dashboard sessions (`hsu_…`) are different credentials. Shop routes use `auth: 'user'` and reject API keys, including admin keys; connector routes ignore sessions. Linking a shop to connector accounts is Feature 5.

## D8: authorization model
Roles `owner` | `manager`. All shop routes derive access from `memberships` via one helper (`requireRole` in `routes/shops.ts`); the shopId in the URL is never trusted by itself. Non-members get 404 (no existence leak); under-privileged members get 403. Owner: update shop, add/change/remove members. Manager: read shop and members, leave the shop. Last owner cannot be demoted or removed (transactional). Any user may create a shop and becomes its owner. Open self-registration is on by default (`HEPSON_ALLOW_REGISTRATION=false` disables); registration grants no shop access. Members can only be added if the user already registered (no invitations/email yet).

## D9: Phase 1 schema guard scoped
The test forbidding credential-like column names now skips `users` and `user_sessions` (hashed dashboard passwords/session ids); Phase 1 connector tables remain guarded.

## D10 (Feature 3): catalog model
Prices are integer minor units (`priceMinor`, kopiykas for UAH) with a per-product ISO currency defaulting to the shop's; a variant may override the price (`null` = inherit). Every product has >= 1 variant; a product without options gets one default variant (`options {}`) from `sku`/`stock`. SKU lives on variants, is trimmed, uppercased, `[A-Za-z0-9._-]{1,64}`, unique per shop (unique index `shop_id, sku`). Stock is on variants with DB CHECK >= 0; `adjustStock` is a single conditional UPDATE (race-safe). No hard delete: deactivate (`active=false`) so future order drafts keep valid references. Duplicate option combinations within a product are not rejected (known gap).
Search uses a `search_text` column folded with JS `toLowerCase()` because SQLite `LIKE`/`lower()` is ASCII-only and would break Cyrillic. Tokens are ANDed; `%`/`_` escaped. Fine for thousands of products; swap for FTS5 if needed.
Permissions: owner creates/edits products and variants; any member (manager too) reads and changes stock (`POST .../stock` with `{delta}` or `{set}`). All repository methods take `shopId` first and filter on it, including id lookups; a foreign id is "not found".

## D11 (Feature 4): conversation model
Phase 1 `conversations`/`messages` stay connector-scoped (by account, fingerprint-deduped). Phase 2 uses separate `customers`, `shop_conversations`, `shop_messages` (named to avoid clashing with Phase 1 exports); Feature 5 maps connector data into them. `channel` is a free lowercase key (`instagram`, `website`), not a DB enum, so new channels need no migration. Identity: customer unique on (shop, channel, external id); conversation on (shop, channel, external id) and it must keep one customer (a conflicting customer id is `ConversationConflictError`); message on (conversation, external id), so `ingestMessage` is idempotent and a duplicate changes nothing. Order is a per-conversation `seq` (assigned in the insert transaction); `occurred_at` is the channel time, else ingest time, and `last_message_at` is the max.
Attribution: incoming => `customer`/`received`; outgoing => `ai|human|system`, `human` requires a `sender_user_id` who is a member of the shop (DB CHECKs enforce direction/sender consistency). Delivery: outgoing starts `pending` or `sent`; `sent` requires the channel message id (no fabricated acks). Transitions: pending -> sent|failed|uncertain, uncertain -> sent|failed; `sent`, `failed`, `received` are final. A new inbound message reopens a closed conversation. Routes are read-only and any member may call them (non-member 404); writes come from ingestion (F5), the agent (F6) and handover (F8). A `human` message may have no `sender_user_id` (reply made outside Hepson); `uncertain` may be recorded directly for an outbound message. Known gap for Feature 6/8: when the agent sends through the connector, the shop-side `pending` row and the mirrored Phase 1 message must be reconciled (D12 mirrors by Phase 1 message id, so a pending row needs to adopt that id).

## D12 (Feature 5): connector accounts linked to shops, mirrored by a bridge
> Status 2026-10-29: describes the frozen browser adapter path (D22). The mirroring rules stay valid for it. Whether `instagram-official` reuses this bridge is decided in the P1 session (see D23).

`store_accounts.shop_id` (nullable FK, one shop per account) is the link. Only an admin API key links/unlinks (`PUT|DELETE /v1/accounts/:accountId/shop`): a shop owner must not claim an Instagram account by id. Members only list their shop's channels. Unlink stops mirroring but keeps already-mirrored shop data; relinking to a different shop is refused until unlinked.
Phase 1 stays the source of truth for reading Instagram. `ChannelBridge` (called by `ConnectorService` after each stored message, and on link and boot) copies into the Phase 2 tables. Mapping: channel `instagram` (connector `mock` => channel `mock`); customer = the other party of the thread, external id = provider conversation id (handles can be missing or change; display name from thread title, handle when exactly one is known); external message id = Phase 1 message id, so mirroring is idempotent and the connector's own adoption of uncertain sends carries over (uncertain -> sent via `setDeliveryStatus`). Outgoing messages are `human` with no user (Phase 1 cannot tell the owner typing in Instagram from an API client). Mirror failures are logged and never break connector sync; boot backfill repairs gaps.
Known gaps: Phase 1 data retention purge and `deleteAccountData` do not touch shop data, and a re-sync after a wipe re-mirrors messages under new Phase 1 ids (duplicates in the shop); backfilled history has `occurred_at` = observation time because Instagram times are relative; group chats are mirrored like 1:1 threads (Phase 1 does not support them); the agent (F6) must not treat backfilled or old messages as new customer questions.

## D13 (Feature 6): agent design
> Status 2026-10-29: extended by D23-D26. The trigger described here (connector `message.received`) is the browser path; webhook channels (Instagram official, Telegram) get their own trigger in P1/P2 and keep the one-run-per-message guarantee. The reply guard gains policy, delivery-date and payment-state coverage in P3-P5. "One shared bot" and the tool list will change; the "model output is never authoritative" rule does not.

**Trigger**: the connector's `message.received` event (emitted only for genuinely new inbound messages after the first full sync, D12), looked up in the shop tables via account link + provider conversation id + Phase 1 message id. Mirrored history, backfill and relinking never trigger the agent. `ai_runs.trigger_message_id` is unique, so one inbound message gets at most one run, also across restarts; runs left `running` by a crash are marked `failed` at boot. A conversation is processed serially. The reply is dropped (`superseded`) when a newer message exists by the time it is ready, and the next run answers the whole burst. The agent skips a conversation while an `escalations` row is open.
**Model access**: `LlmClient` interface; `OpenAiClient` is plain `fetch` to Chat Completions with function calling (no SDK dependency), 30 s timeout, up to 3 attempts on 429/5xx/network, response bodies never copied into errors or logs, key only in the Authorization header. Needs `OPENAI_API_KEY` and `HEPSON_OPENAI_MODEL` (no default model on purpose: availability depends on the account). Without both the agent is simply not created. The shop owner must also enable it (`shop_ai_settings.enabled`, default off). Tests use `ScriptedLlm`; no test or script calls OpenAI.
**Tools and truth**: the model gets read tools (`search_products`, `get_variant`, `quote_order`), `create_order_draft` and `escalate`. Prices, stock and totals are computed by the server from the catalog; tool arguments are strict zod schemas (unknown keys rejected) and carry no prices or ids other than SKUs. `reply guard` (`agent/guard.ts`) is a heuristic backstop: every price in the reply must equal a price a tool returned in that run (so totals must come from `quote_order`), every stock figure must be a tool stock, "in stock"-style claims need a catalog lookup in the run, length <= `HEPSON_MAX_MESSAGE_LENGTH`. A blocked reply gets one repair round, then the conversation is escalated and nothing is sent. Known limits: it parses common Ukrainian/Russian/English phrasings only; it cannot judge qualitative claims (material, delivery time) - the prompt forbids inventing them and the owner notes cannot lift the hard rules.
**Failure policy**: a model error records a `failed` run (`LLM_<status>`), sends nothing and does not escalate (the next customer message tries again). A send rejected before queueing marks the shop-side row `failed`; `uncertain` stays `uncertain` and is never retried (connector rule). Run rows hold codes only, never customer text. Token usage per run is stored for F9.
**Escalation**: an open escalation mutes the agent in that conversation until a member resolves it. The model may still send one holding message in the same turn. Notifications are F8.

## D14 (Feature 6): reconciling the agent's own sends (closes the D11 gap)
Before sending, the agent records an outgoing `ai` message `pending` without channel id. When the connector later stores the sent message, `ChannelBridge.mirrorOne` first calls `ConversationRepository.adoptPendingOutbound`: the newest `pending`, id-less `ai` message of that conversation with identical (trimmed) text takes the Phase 1 message id and the `sent`/`uncertain` status, instead of adding a `human` row. If nothing matches (a person typed it in Instagram), the old `human` behaviour applies. The uncertain -> sent resolution from D12 continues to work because the id is shared. Edge: identical text sent by a human at the same moment can be adopted by the pending AI row (accepted).

## D15 (Feature 7): order drafts
> Status 2026-10-29: extended by D25 (state machine) and D26 (autonomy). "Approval is a human decision" now holds for `approval_required` only; "does not message the customer" is replaced by P6. "Stock reservation before approval" is no longer a goal: stock is taken at approval (D25).

A draft is created by the AI tool only (no member creation yet) from SKUs and quantities; the server snapshots name, options and unit price per line and computes the total, all lines must be active, in stock and in one currency. Creating a draft does not reserve stock. Status: `pending_approval` -> `approved` | `rejected`; `cancelled` is used when a newer AI draft replaces a pending one in the same conversation. Approval is a human decision by any member (owner or manager) and is the only operation that changes stock: one conditional `UPDATE ... stock >= qty` per line inside a transaction, so a draft that can no longer be covered fails whole and stays pending. Re-approving or rejecting a decided draft is refused. The agent is told that a draft is not a confirmed order and must say so to the customer; approval does not message the customer (F8/later). Chosen over decrementing at draft time to avoid the AI locking stock with unconfirmed chats; trade-off: stock can run out between draft and approval, which the approval check reports.

## D16 (Feature 8): human takeover
> Status 2026-10-29 (P1 built): the official path records an echo of a message typed in the Instagram app as a `human` row but does **not** auto-pause the AI, because echo shape and text fidelity are unverified (a mismatch between our pending text and Meta's echo would pause wrongly). Decide after the live capture. **Re-evaluate in P1's live check.** The "cannot tell a person typing in the Instagram app from the API" limit belongs to the browser adapter. The official API is expected to deliver `message_echoes` for messages sent from the Instagram app, which would allow auto-pause when someone other than Hepson replies. Not verified; check against Meta's current webhook documentation and a live account before changing the rule. Until then the rule below stands.

The pause is a per-conversation flag on `shop_conversations` (not a second escalation kind): an escalation means "the AI asks for help", a pause means "a person decided to handle this". Both mute the agent; they are independent, and resolving an escalation does not resume a pause. Any member may pause, resume and reply (same trust as resolving an escalation). A human reply through `POST .../messages` pauses first and then sends, so the agent cannot answer in between; the member resumes explicitly. The reply is a `human` row with `sender_user_id`, sent via the same connector queue as the agent (`services/shop-sender.ts`, key `human:<messageId>`); before recording anything a dry-run `requestSend` applies the connector's checks, so an impossible send leaves no `failed` row and no pause. No client idempotency key yet: a retried request after a timeout sends a second message. A person typing in the Instagram app is NOT auto-paused: Phase 1 cannot tell that from an API client (D12), and pausing on every outgoing message would also pause on the agent's own replies. Paused conversations still ingest customer messages; the run is recorded as `skipped`/`AI_PAUSED` so the audit trail shows why nothing was answered.

## D17 (Feature 8): Telegram notifications
> Status 2026-10-29: still valid for owner notifications. That shared bot is Hepson's operator bot, not a shop credential. The customer-facing Telegram channel uses a separate bot per shop (D27); the two must not share a token or an environment variable.

One shared bot (token in the environment, never in the DB), one chat id per shop in `shop_notify_settings` (numeric id or `@channel`; owner writes, members read). No token or no chat id = silent. Events: a newly opened escalation (not a repeat while one is open) and a new AI order draft. Message text is plain (no parse mode, so customer-influenced text cannot inject markup) and holds the shop name, the customer's display name or handle, the escalation reason or the draft's item count and total; no phone, address, or message text. It is Ukrainian for `uk` shops, English otherwise. Delivery is fire-and-forget with one attempt: a failure logs only the shop id and a short code (the Bot API puts the token in the URL, so URLs and error messages are never logged), and the API remains the source of truth. A paused or escalated conversation does not notify on every new customer message (would be spam; a later feature can add a digest). Trade-off: the bot token is shared across shops, so a shop owner who types another shop's chat id can only cause messages to that chat if the bot is a member there; chat ids are not verified by a handshake yet.

## D18 (Feature 9): statistics
Computed on demand from `ai_runs`, `shop_messages`, `escalations`, `order_drafts`, `customers`, `shop_conversations` (no counters to drift). Time is the row's `created_at` (Hepson ingest time): mirrored history is counted when it was first mirrored, not when Instagram says it happened (the Instagram time is relative, D12), so linking an account with old history adds those messages to that day's totals. Buckets are UTC days. `replyRate` = replied / runs that reached a verdict (all but `running`, `skipped`, `superseded`). Tokens are reported, not priced: model prices change and differ per account.

## D19 (Feature 10): website chat
**Tenancy and auth layers** (these are the only unauthenticated shop-facing routes; they exist because a website visitor has no account): (1) the public widget key (`hwk_`, in the snippet, not secret) selects the shop; unknown, disabled and rotated keys all answer 404. (2) The request `Origin` must equal one of the shop's allowed origins (exact scheme/host/port, lowercased, no wildcards, max 20; empty list admits nobody; a missing Origin is refused). This stops other sites from embedding the chat in a visitor's browser, it is NOT authentication: a script outside a browser can send any Origin. (3) Each visitor holds a random session token (`hwv_`, header `x-hepson-visitor`, sha256 stored, 30 days by default); a token only works with its own shop's key and sees only its own conversation (the conversation is derived from the session, never from a client-supplied id). (4) Rate limits.
**CORS**: only an allowed origin of an enabled key gets `Access-Control-Allow-Origin`; preflights follow the same rule, so a browser on another origin cannot read responses either.
**Abuse limits** (env-tunable, in memory per node like D6): sessions 20/h per IP, messages 10/min per session and 40/min per IP, 2000 visitor messages per shop per UTC day (this also caps AI spend), 1000 characters per message, one `429` with `Retry-After`. Behind a reverse proxy set `HEPSON_TRUST_PROXY=true`, otherwise all visitors share the proxy's IP; set it only if the proxy overwrites `X-Forwarded-For`, because clients could otherwise spoof their IP. No CAPTCHA; a determined attacker rotating IPs is limited only by the daily cap.
**Delivery model**: the channel is hosted by Hepson, so no connector is involved (`Delivery.kind = 'internal'`). An outgoing message becomes `sent` as soon as it is stored with a generated `web:<uuid>` id, and the visitor's poll (3 s, only while the panel is open) picks it up; that is an honest "available to the visitor", not a read receipt. Visitors see only incoming messages and `sent` replies, with a `fromAi` flag (the widget labels AI replies "Віртуальний асистент" so people know they talk to a bot), no user ids, no run or draft data. The agent answers through `SalesAgent.triggerInternal`; everything else (guard, escalation, pause, drafts, notifications, stats) is the shared code path.
**Customer identity**: a visitor is `Відвідувач xxxx` (random id) until they say who they are in the chat; the AI's order tool collects name/phone/delivery as before. Visitor text reaches the model as untrusted customer text (D13). The widget inserts server text with `textContent` only.
**Privacy**: no cookies; the token sits in the visitor's `localStorage` of the shop's site. Shops are responsible for a privacy notice on their site (the API stores message text and the hashed token; IPs are not stored).
Known gaps: tokens are bearer secrets in `localStorage` (any XSS on the shop's own site can read them, same as the shop's own session risk); polling instead of SSE; no per-shop IP/abuse dashboard; session purge keeps conversations and messages.

## D20 (Feature 11): dashboard skeleton
A separate small React/Vite app (`apps/dashboard`), not an extension of the dev console: the dev console is an admin-key tool for connector accounts; the dashboard uses user sessions (D6/D7) and shop-scoped routes only. No UI library, no router (tabs in state), one CSS file, polling instead of SSE. The bearer session token is kept in `localStorage` (D6 trade-off: XSS would expose it; a cookie session with CSRF protection is the later hardening). A 401 anywhere returns the user to the login form. The UI shows controls by role but never decides access: the server answers 403/404 (D8). Ukrainian labels are inline strings; add i18n when a second language is needed. Instagram account linking stays an admin task (D12).

## D21 (Feature 12): catalog import and hardening
> Status 2026-10-29: the "CSV only" and "no URL fetch" parts are revisited by P8, under the outbound allow-list of D22. Google Sheets is fetched only from the fixed Google host; no owner-supplied arbitrary URL is ever fetched.

**CSV only.** Excel needs a parser dependency with a history of security advisories and macro/format surprises; a shop can "Save as CSV" (the importer reads Excel's `;` delimiter and decimal comma). **No feed URLs:** fetching an owner-supplied URL from the server is an SSRF vector (internal addresses, metadata endpoints) and needs a scheduler, allow-listing and failure handling; add it deliberately with an egress policy, not as a side effect.
**Semantics:** key = SKU within the shop. Existing SKU = update, new SKU = create; empty cells never overwrite; `stock` is SET (a file is a snapshot, but it can overwrite stock that changed since the export, e.g. by an order approval: import right after exporting). `active` applies to the variant, not the product. Rows sharing `group` form one product (name/description/price must agree, per-variant price goes in `variant_price`); no `group` = one product per row. Prices are major units with `.` or `,` and at most two decimals; thousands separators are rejected as ambiguous. Whole file is one transaction: any error, or `dryRun`, rolls back, so the preview is exactly what a real run does (same code path). `dryRun` defaults to true so a bare API call never writes. Row errors are a 200 with `applied: false` (a normal answer for a preview); a malformed file or header is a 400. Limits: 5000 rows, 2 MB; the larger body limit applies to that route only.
**Hardening:** `/ready` answers 503 if SQLite fails, `/health` stays pure liveness. `no-store` on `/v1/*` and `/public/*` unless a route sets its own cache policy (the widget script does). Dead user sessions (expired or revoked for over 7 days) are deleted every 6 h. `pnpm backup` uses SQLite's online backup (consistent under WAL). It excludes `profiles/` on purpose: those hold live Instagram logins and need an owner decision about where they are stored (D-level rule: Hepson never handles credentials). Restore is a manual file copy with the API stopped.

# Pivot decisions (2026-10-29)

Nothing in D22-D28 has been implemented or run against Meta, Telegram, Nova Poshta, Monobank or WayForPay. Statements about those platforms record what the owner's brief and the author's understanding of their public documentation say. Each P-session must re-check them against the current official documentation and mark what it verified live.

## D22 (2026-10-29): pivot to compete with NovaSale on official APIs only
**Context.** NovaSale (novasale.app) is a Ukrainian AI-CRM that sells "from message to waybill (TTN)". It is a Meta Tech Provider on the official Instagram API, also serves Telegram, and ships: product search by text or photo, FAQ from a shop knowledge base, upsell and alternatives, address collection, WayForPay/Monobank payment links or cash on delivery, Nova Poshta TTN creation and status, manager handoff, a public storefront, CRM, analytics, imports and exports. Plans are capped by AI replies per month. Hepson's Phase 1 reads and sends Instagram DMs by automating the web UI, which may breach Instagram's terms (`docs/LIMITATIONS.md`) and is a business risk that blocks any paying customer.
**Decision.** (1) Build toward the same core loop, message to paid order to TTN, on official APIs only. (2) `packages/instagram-browser` is frozen: keep code and tests, disable it by default behind an explicit flag (set in P1), mark it deprecated in docs, put no new work into it, delete it only after the official adapter is live-verified. (3) No scraping of any platform. (4) Hepson never holds customer money (D24). (5) Every external credential is per shop and encrypted (D28). (6) Outbound HTTP goes only to an allow-list of hosts: Instagram Graph API, Telegram Bot API, Nova Poshta API, Monobank and WayForPay APIs, the configured LLM provider, plus Google's fixed spreadsheet-export host once P8 needs it. All production `fetch` calls go through one egress helper that refuses any other host; the existing OpenAI client and Telegram notifier move onto it in P1. (7) Product principles, to keep and not as marketing: **verifiable honesty** (the reply guard blocks any price or stock figure no tool returned; extend the rule to policies, delivery dates and payment state), **owner control** (per-shop autonomy, D26), **lower entry price plus a website chat widget** alongside DMs (the widget exists, D19).
**Constraint: no registered business (FOP) yet.** Meta Business Verification and App Review for Advanced Access come later. Until then the Meta app stays in Development mode with Standard Access, which works only for Instagram professional accounts that have a role on the app: the owner's own account and a few pilot shops added as Instagram testers with their consent. Code must treat the move to Advanced Access as configuration (app id, secret, review-approved scopes), not a rewrite. Hepson's own subscription billing also waits for the FOP.
**Alternatives.** Keep the browser adapter as the main channel (rejected: terms risk, fragile, one-account-per-profile). Wait for the FOP before any work (rejected: wastes months; Development mode is enough to build and demo). Telegram first (kept as P2; Instagram is where Ukrainian shops sell).
**Consequences.** The Phase 1 live-verification work is closed, not extended. Docs, `AGENTS.md` and the roadmap point at the P-series. The egress helper and the browser flag are the first code changes of P1. The pilot cannot exceed the accounts that Meta allows in Development mode, so the first "customers" are testers.

## D23 (2026-10-29): Instagram via "Instagram API with Instagram Login"
**Context.** The official messaging path that does not require a Facebook Page is Instagram API with Instagram Login (business login). It supersedes `docs/FUTURE_META_ADAPTER.md`, which assumed the same API family but a console-driven flow and App Review as a prerequisite.
**Decision.**
- **Connect.** Dashboard OAuth (business login). The `state` parameter is a single-use random value bound to the logged-in user and the shop, checked on the callback (no cross-shop or cross-user linking). The short-lived code is exchanged server-side for a long-lived token (about 60 days) and stored per D28. Requested scopes are the minimum for reading and replying to messages (as understood: `instagram_business_basic`, `instagram_business_manage_messages`; confirm the exact names in P1). The Instagram professional account id is stored as a non-secret reference on the channel account.
- **Token lifetime.** A scheduled job refreshes tokens ahead of expiry (as understood, only a token that is at least 24 hours old and not yet expired can be refreshed; confirm). A refresh that fails with an auth error marks the channel as needing reconnection, notifies the shop through the existing escalation/Telegram path, and stops sending. It is never retried in a loop.
- **Inbound.** Webhook route with the `GET` handshake (`hub.challenge`, a global verify token from the environment) and `POST` for `messages` events. `X-Hub-Signature-256` is HMAC-SHA256 of the **raw** body with the app secret (environment, global to Hepson, not per shop), compared in constant time **before** any parsing; a bad or missing signature gets 401 and nothing is stored. Fastify must expose the raw body for this route only. The shop is resolved from the entry's Instagram account id; an unknown account is acknowledged and dropped. Messages dedupe on the message id (unique per conversation, D11), so Meta's retries and replays are harmless. The route answers quickly and does its work after storing the event. Echo events (messages sent by the account itself) are stored as outgoing messages and never trigger the agent.
- **Outbound.** Send API. Meta offers no idempotency key, so Hepson keeps its own: a send is recorded `pending` first, an ambiguous outcome (timeout after the request left, 5xx with no body) becomes `uncertain` and is never auto-retried (existing invariant); a clear Meta rejection is `failed`.
- **24-hour window.** The server records the time of the customer's last inbound message and refuses to send outside 24 hours of it, before calling Meta, with a distinct error (`OUTSIDE_MESSAGING_WINDOW`). The agent does not send then: it records the run as skipped or escalates, and notifies the shop. Human-agent replies beyond 24 hours (as understood, up to 7 days with a message tag) are allowed only for human-typed messages and only after Meta approves the Human Agent feature; until then humans are bound by the same 24-hour rule. Windows are enforced by Hepson's clock plus webhook timestamps; Meta's rejection remains the final authority.
- **Development mode.** Standard Access only: accounts with a role on the app. Webhooks in this mode reach only those accounts (as understood; confirm in P1). The pilot list is the owner's account plus testers who consented in writing.
- **Reuse of the connector layer (open design point for P1).** `MessagingAdapter` and `ConnectorService` already provide the send queue, `uncertain` handling, idempotency and SSE, and the registry already has an empty `instagram-official` slot; but the Phase 1 tables are account-scoped, browser-shaped and subject to the 30-day retention purge. Recommendation: implement `instagram-official` as a `MessagingAdapter` whose messages arrive by webhook rather than polling, and let the existing `ChannelBridge` mirror them into shop tables, which keeps send/uncertain/SSE behavior identical and keeps the agent trigger unchanged. The P1 session must confirm this against the code (polling assumptions in `ConnectorService`, retention purge interacting with webhook-only data) and may instead write straight into shop tables as the website chat does (D19). Record the outcome as an amendment to this decision.
- **D16 re-evaluation.** With echo events, auto-pause when a non-Hepson sender replies may become possible. P1 checks this live and amends D16.
**P1 amendment (2026-10-29, adapter shape decided).** `instagram-official` is **not** a `MessagingAdapter` and does not use `ConnectorService`/`ChannelBridge`. Reasons found in the code: `ConnectorService` is built around polling workers, account-scoped Phase 1 tables and a 30-day retention purge, none of which fit webhook-fed data; its send queue exists to serialize one browser per account, which the Send API does not need. Instead `InstagramService` (`apps/api/src/services/instagram.ts`) writes straight into the shop tables like the website chat (D19) under channel key `instagram-official` (distinct from the frozen browser path's `instagram`, so thread ids never mix). Customer and conversation external id = the customer's Instagram-scoped id; message external id = Meta's `mid`. Inbound: signed webhook -> `ConversationRepository.ingestMessage` (unique per conversation, so Meta retries are harmless) -> `SalesAgent.trigger` (one run per message, D13). Outbound: `deliverPending` kind `instagram` -> `InstagramService.send`: connection and 24-hour window checked first, one attempt, 5xx/timeout/no `message_id` = `uncertain` (never retried), clear 4xx = `failed` with a short code, token rejection (HTTP 401 or Graph code 190/102/463/467) = credential `needs_reconnect`, one owner notification, no further sends. Echoes: our own pending row is adopted by text (`adoptPendingOutbound`, like D14); an unmatched echo is stored as `human`. The window start is the newest incoming `occurred_at` of the conversation (webhook timestamp clamped to receive time). Tokens: long-lived (about 60 days), refreshed by a 6-hourly job when they expire within `HEPSON_INSTAGRAM_REFRESH_WITHIN_DAYS` (default 14); an expired or rejected token is not retried. One Instagram account links to one shop and one shop has one account. Known gap: an `uncertain` send whose echo arrives later is not reconciled (adoption targets `pending` rows only), so a duplicate `human` row may appear.
**Not verified against Meta.** Endpoint paths, response shapes, the `#_` code suffix, scope names, subcodes `2534022`/`2018278` for the window, Graph error numbers, API version `v23.0` (`HEPSON_META_API_VERSION`) and whether the echo `mid` equals the Send API `message_id` are written from documentation memory; fixtures in `tests/integration/instagram.test.ts` say so. The live check replaces them.
**Alternatives.** Instagram API via Facebook Login and a linked Facebook Page (rejected for now: many shops have no Page; extra permissions). Keep browser adapter (D22). Polling the Graph conversations endpoints instead of webhooks (kept only as backfill/repair, not primary).
**Consequences.** Webhooks need public HTTPS from day one (a tunnel for local checks). Hepson operates one Meta app; its app secret and verify token are operator secrets. Recorded webhook fixtures in P1 tests are written from the documentation until a live capture replaces them, and say so.

## D24 (2026-10-29): payments - Hepson never handles money or card data
**Context.** The earlier rule (`PROJECT_CONTEXT.md`, D15 era) was "the AI never takes payments". The product must still get customers paid inside the chat.
**Decision.** The rule becomes: **the AI never handles money or card data; it relays a payment link that the server generated with the shop's own acquiring credentials.** Funds go from the customer straight to the shop's merchant account; Hepson is not a merchant, holds no balance, stores no card data and never sees it. Supported first: Monobank acquiring (the first pilot shop uses it, owner decision 2026-10-29), then WayForPay (P5), each with the shop's own credentials (D28). Payment state is changed only by a verified provider event (webhook with the provider's signature check) or by Hepson calling the provider's status endpoint; never by the model, never by the customer's words ("I paid"). Details:
- The link is created by server code when an order enters `awaiting_payment` (D25), from the order's server-computed total and currency. It is not produced by a model tool call and no tool accepts an amount. The link is sent to the customer by the server using fixed template text, not model-composed text.
- A verified event is applied only if provider invoice id, amount and currency match the stored order; a mismatch does not mark `paid`, it records a flagged event and opens an escalation.
- Event handling is idempotent (dedupe on provider event/invoice id plus status); out-of-order events cannot move an order backwards. A reconciliation job asks the provider for the status of `awaiting_payment` orders, so a lost webhook does not strand an order.
- The agent gets a read-only order-status tool; the reply guard rejects any "paid / оплачено / payment received" claim unless that tool returned `paid` in the same run (extends D13's rule).
- Refunds are human-only and happen in the provider's cabinet; Hepson can record `refund_requested` and notify the shop.
- An unpaid link expires after 24 hours and the order is cancelled with restock, with one customer reminder before that (D25).
- Use the provider's test/sandbox mode where one exists, mocks otherwise. Webhook signature schemes (Monobank's public-key signature, WayForPay's HMAC) are as understood and must be re-read from the provider documentation in P5.
**Alternatives.** Hepson as merchant or payment facilitator (rejected: holds client money, licensing and AML exposure, needs a legal entity). Model tool `create_payment_link(amount)` (rejected: model-supplied amounts break D13). Trusting the customer or a manager click as "paid" (rejected as the only source; a human "mark as paid" for bank transfers outside the providers is possible later as an explicit audited manual action, not part of P5).
**Consequences.** Each shop needs its own merchant account with a supported provider, so onboarding takes the shop through that contract first. Webhook endpoints are public and signature-gated, like D23. The reply guard and stats need the order-status states of D25.

## D25 (2026-10-29): order state machine
**Decision.** Extend `order_drafts` (D15) into a full lifecycle. States and transitions, all made by server code or a human member, never by the model:
`pending_approval` -> `approved` -> (`awaiting_payment` | `cod_confirmed`) -> `paid` (online path only) -> `shipped` (TTN created) -> `delivered` | `returning` -> `returned`.
Return branch (owner decision 2026-10-29): `shipped` -> `returning` when Nova Poshta reports the parcel refused or on its way back to the sender; `returning` -> `returned` only when a member confirms the parcel is back at the shop. The server notifies the shop on entering `returning`. No stock is restored on `returning`; stock is restored once, atomically, on the member's confirmation into `returned`.
Side exits: `rejected` (from `pending_approval`; kept from D15 so history and stats stay readable), `cancelled` (from `pending_approval` by supersede as today, and from `approved`, `awaiting_payment`, `cod_confirmed`, `paid` by a human or a payment timeout, always before shipping), `refund_requested` (from `paid`, `shipped`, `delivered`, `returning`, `returned`; human-only, D24). `delivered`, `returned`, `cancelled` and `rejected` are final apart from `refund_requested`.
- **Approval.** `approved` is reached by a member (`approval_required`) or by the server in `auto_confirm` (D26). The payment method is already chosen in the checkout data; approval moves to `awaiting_payment` (online) or `cod_confirmed` (cash on delivery).
- **Stock.** Stock is taken at approval, atomically and all or nothing, exactly as today (D15). There is no reservation before approval. New: leaving `approved`-and-later states through `cancelled` restores the stock of that order in the same transaction, once (guard against double restore). An `awaiting_payment` order expires after 24 hours (default, per-shop setting) and is cancelled with restock. One reminder is sent to the customer before expiry (default 6 hours before; server-templated text, once per order, idempotent). The reminder only applies to an order that a member approved (or auto-confirm approved) and whose link was sent. If the channel cannot carry it (Instagram window closed, D23), the shop is notified instead. Leaving `returning`/`returned` through `cancelled` is not allowed.
- **TTN.** `shipped` requires a Nova Poshta TTN number returned by the NP API; `delivered` comes from NP tracking status polling. A prepaid order may only get a TTN from `paid`; COD from `cod_confirmed` (relevant to P4/P5 ordering, see ROADMAP).
- **Audit.** Every transition writes an event row (who or what: member id, `system:auto_confirm`, `provider:monobank`, `system:timeout`; from, to, time). Statistics (funnel, AI vs human counts) derive from these rows.
- **Refusal count and COD protection** (owner decision 2026-10-29). Each parcel that enters `returning` because the recipient refused counts as one refusal against the customer, counted per shop by normalized phone number from the checkout data (and by customer id when no phone exists); refusals are never shared across shops. A member can also record or remove a refusal by hand. When a customer's count reaches the shop's limit (default 1, configurable 1-3, 0 disables the rule), the server stops offering cash on delivery: the checkout tool lists only prepaid methods, a draft with COD for that customer is refused, and `auto_confirm` (D26) never confirms COD for them. The model is told only the available methods; it cannot override the rule. The reason shown to staff is the count, not a judgement of the person. The shop pays return shipping on refused COD parcels, which is why the limit exists.
- **Open:** whether a member may restock only some lines on `returned` (damaged goods). Default: all lines, member may skip restock with a note.
**Alternatives.** Keep drafts and a separate `orders` table (rejected: duplicates items and snapshots). Reserve stock at draft time (rejected in D15, still rejected). Free-form status text (rejected: guard and stats need a closed set).
**Consequences.** One migration widens the status enum and adds events plus checkout and delivery columns (P4/P5 split it). Existing tests on `pending_approval/approved/rejected/cancelled` keep passing.

## D26 (2026-10-29): autonomy levels per shop
**Decision.** `shop_ai_settings.autonomy` is `approval_required` (default) or `auto_confirm`; only an owner changes it, and the change is audited.
- `approval_required`: the AI creates a draft, a member approves (today's behavior).
- `auto_confirm`: the server approves the draft by itself only when all checks pass at that moment: every line active and in stock (the same atomic stock update as a human approval), totals computed by the server from the catalog, the checkout data complete and valid (name, phone, a resolved Nova Poshta city and branch, a chosen payment method), the conversation not paused and without an open escalation, and the order within an optional owner-set value cap. Anything else leaves the draft `pending_approval` for a human. A COD order for a customer at or over the shop's refusal limit is never auto-confirmed (D25). The transition is attributed to `system:auto_confirm`, not to a member.
- The AI never refunds, never marks `paid`, and never changes autonomy.
**Alternatives.** A single global switch (rejected: shops differ). Model-decided confirmation (rejected: model output is never authoritative). Value-threshold only (kept as the cap inside `auto_confirm`).
**Consequences.** Supersedes the "never final order confirmation" scope line and the "approval is a human decision" sentence in D15: in `auto_confirm` the policy choice is the owner's and the verification is server-side. Stats must separate AI-confirmed from human-confirmed orders.

## D27 (2026-10-29): Telegram as a customer channel
**Decision.** Telegram Bot API as a second customer channel, **one bot per shop**, created by the shop owner in BotFather; the token is a per-shop credential (D28). Inbound by webhook: Hepson registers the webhook with a per-shop random `secret_token` and rejects any update whose `X-Telegram-Bot-Api-Secret-Token` header differs (constant-time). The webhook path carries an opaque random identifier, never the token. Channel key `telegram`; the customer's external id is the chat id; the message external id is `<chat_id>:<message_id>` because Telegram message ids are only unique per chat. Updates are deduped on `update_id` and on the message id. There is no 24-hour window; a user who blocked the bot yields a send failure recorded as `failed`. Telegram has no Phase 1 side, so it follows the `ChannelBridge` **pattern** (normalize, ingest idempotently through `ConversationRepository`, trigger `SalesAgent` once per inbound message, deliver and record the outgoing row) the way website chat already does (D19), not the Phase 1 connector mirror. A conversation of the same person on two channels is not merged automatically; "one shared history per customer" is a later feature that needs an explicit identity-linking rule (phone number the customer gave and the shop confirmed).
**Alternatives.** One shared Hepson bot for all shops (rejected: customers would see Hepson's bot instead of the shop's, and one leaked token exposes every shop). Telegram long polling (rejected: webhooks are already required for Instagram). Telegram business-account chat automation (not assessed; revisit if shops ask).
**Consequences.** `HEPSON_TELEGRAM_BOT_TOKEN` stays only for D17 operator notifications and must not be reused for customers. Webhook setup and `deleteWebhook` on disconnect are part of P2.

## D28 (2026-10-29): per-shop credential storage
**Context.** Hepson will hold per-shop secrets: Instagram tokens, Telegram bot tokens, the Nova Poshta API key, the Monobank token and the WayForPay merchant secret. Phase 1 rule "Hepson handles no credentials or cookies" stays true for Instagram **passwords and cookies**; provider tokens and API keys are now stored, encrypted.
**Decision.**
- **Envelope encryption with node:crypto, no new dependency.** A master key (key-encryption key, 32 random bytes) comes only from the environment, with a version number. Each secret gets its own random data key and nonce; the secret is encrypted with AES-256-GCM using the data key; the data key is wrapped with the master key (also AES-256-GCM). The additional authenticated data binds shop id, credential kind and row id, so a ciphertext copied to another row or shop does not decrypt. Stored: key version, wrapped data key, nonces, ciphertext, tags. Never stored: plaintext.
- **Table** `shop_credentials`: id, shop id, kind (`instagram`, `telegram_bot`, `nova_poshta`, `monobank`, `wayforpay`), status (`active`, `revoked`, `needs_reconnect`), the ciphertext fields, key version, created/rotated/last-used/revoked times. One active row per shop and kind (new save replaces the old one, which is overwritten, not kept).
- **No read-back.** Only the owner can save or delete a credential. Every API after saving returns the kind, status and times, never the value or any part of it. Logs, error messages, audit rows and run rows never contain it (pino redaction paths added; URLs that embed tokens are never logged, as in D17). The plaintext exists in memory only for the duration of one outbound call.
- **Master-key rotation.** A script re-wraps every data key from the old master key version to the new one without touching the secrets (cheap, restartable, idempotent). Environment carries the current key and, during rotation, the previous one. Rotation is documented and tested in P1 (the first credential holder).
- **Provider revokes or token invalid.** An authentication failure from the provider marks the credential `revoked` or `needs_reconnect`, stops all use, and notifies the shop. No retry with the same token. Owner re-enters or re-connects.
- **Lost master key.** Secrets become unrecoverable; every shop must reconnect its integrations. Backups (`pnpm backup`) hold only ciphertext, so the master key must be stored separately from backups and database; losing both is the failure case, and the runbook says so.
- **Compromised master key** together with a database copy means all secrets are exposed: rotate the master key and ask shops to rotate their provider secrets.
- Operator-level secrets (Meta app secret, webhook verify token, OpenAI key, shared Telegram bot) stay in the environment and are not in this table.
**Alternatives.** Plaintext column plus disk encryption (rejected: any DB read leaks everything). A cloud KMS (better long-term; adds a paid service and a dependency, not approved now; the envelope layout keeps the master-key step swappable). libsodium (rejected: node:crypto is enough).
**Consequences.** `HEPSON_MASTER_KEY` becomes a required setting before any credential route works; without it those routes are disabled, not insecure. The credential layer lands with P1 and is reused by P2, P4, P5.
**Implemented in P1 (2026-10-29).** `CredentialVault` + `Keyring` in `packages/database/src/credentials.ts`, table `shop_credentials` (migration `0009`), keys `HEPSON_MASTER_KEY[_VERSION]` and `HEPSON_MASTER_KEY_PREVIOUS[_VERSION]` read from the process environment only (never part of `Config`), `pnpm gen-master-key`, `pnpm rewrap-credentials`. AAD = `hepson.cred.v1|shop|kind|row id` on both the secret and the wrapped data key. No method returns a stored secret: `withSecret(shop, kind, fn)` is the only reader. `last_used_at` is updated on every use. Pino redaction extended (`access_token`, `appSecret`, `secret`, signature headers). Not built: a generic credential route (Instagram has its own connect flow; Telegram/NP/Monobank routes come with P2/P4/P5), a runbook script for the lost-key case.

## D29 (2026-10-30): Instagram via "Unified login" (amends D23)
**Context.** Meta apps created from 2026-10-29 get "API setup with Unified login" instead of "API setup with Instagram login": there is no Instagram app id, and the Instagram-login connect flow of D23 fails with "Invalid platform app". The cause is from Meta's dashboard text plus its Instagram Platform docs; no Meta announcement was found.
**Decision.** The connect and API layer moves to Unified login (Facebook Login for Business with a `config_id`). Everything above the Graph client (webhook ingest, dedupe, echo handling, 24-hour window, `uncertain` sends, vault, needs-reconnect) is unchanged.
- **Connect.** `https://www.facebook.com/dialog/oauth?client_id=<app id>&config_id=<config id>&redirect_uri=…&response_type=code&state=…` (no `scope`; the configuration lists `instagram_basic` and `instagram_manage_messages`). The code is exchanged server side at `GET graph.facebook.com/<ver>/oauth/access_token` with the Meta app id and secret. The result is a Business Integration System User token that belongs to the client's business portfolio, not to the person who logged in. `state` is our own single-use value; Meta's Unified-login page does not document it, so it is an assumption that Meta returns it.
- **Account.** `GET /me/assigned_instagram_accounts?fields=id,username`. Exactly one account must be shared (none or several = refused, dashboard `?instagram=select_one`). Its id is the webhook `entry.id` and the Send API path id.
- **Webhooks.** Per account `POST /<ig id>/subscribed_apps?subscribed_fields=messages` on `graph.facebook.com` with the token. The callback URL, verify token and `messages` field are set on the app's Unified-login tab. Payloads are assumed to keep the `messaging` array shape that Meta documents for Instagram messaging (`entry.id`, `sender`/`recipient`, `message.mid`, `is_echo`).
- **Send / profile.** `POST /<ig id>/messages` with `{recipient:{id}, message:{text}}`; profile by IGSID with `fields=name,username`, best effort. Window error subcodes are still from memory.
- **Token lifetime.** Set by the configuration (default: never expires); there is no refresh call. The token-refresh job is replaced by `expireDue`, which only marks a token expired when Meta reported `expires_in`. A revoked or removed app shows up as an auth error on the next send and moves the channel to `needs_reconnect`. `HEPSON_INSTAGRAM_REFRESH_WITHIN_DAYS` is gone.
- **Configuration.** New `HEPSON_META_CONFIG_ID`; `HEPSON_META_APP_ID`/`SECRET` are now the Meta app's own. Default API version `v26.0` (the version Meta's docs use). `HEPSON_META_OAUTH_BASE_URL` is gone. Egress list: `graph.facebook.com` replaces `graph.instagram.com` and `api.instagram.com`.
- **Requirements from Meta.** The app must be owned by a business portfolio (else the Unified-login tab is missing). The Instagram account must be professional and have "Allow access to messages" on. Standard Access works for people with a role on the app; other clients need Advanced Access and Live mode.
**Not verified (docs only, no live run):** the `state` round trip, the `messages` payload under Unified login, the Send API path with this token, window error codes, the profile call with this token type, and whether a Development/Live app delivers real DMs.
**Polling fallback (2026-10-30).** Real message webhooks were not delivered in the first live test (see `docs/LIMITATIONS.md`). `InstagramService.pollOnce` reads `GET /<ig id>/conversations?platform=instagram&fields=updated_time,messages.limit(25){id,created_time,from,to,message}` (shape confirmed with the live token: keys and types only) and feeds the same ingest as the webhook, so dedupe, echo adoption and the agent trigger are shared. ## D29 follow-up (2026-10-30): webhook failure recovery
The connect flow requires Meta's explicit `{success:true}` subscription acknowledgement before saving the credential and channel together. A failed replacement leaves the existing connection intact. Disconnect cancels pending callbacks; a canceled attempt cleans up its subscription without saving credentials, and overlapping operations for the same shop are refused. A delivery that arrives while its new account subscription is still being confirmed receives HTTP 503 for retry after the channel is saved. Shared-account selection follows pagination and refuses ambiguous or malformed results.

A webhook batch processes its other events even when one fails. Internal persistence or synchronous dispatch failures produce HTTP 503; successfully stored messages dedupe when Meta retries. Permanently invalid inputs are acknowledged and logged by error type only. Inbound storage and synchronous dispatch share a transaction, so a dispatch exception does not leave a stored message that suppresses its own retry. This does not provide a durable agent queue across process crashes.

Polling now starts from `connectedAt` when there is no cursor, so messages between connection and the first poll are eligible while earlier history stays excluded. A failed batch preserves its cursor, equal timestamps are reconsidered using message-id dedupe, and changing the connected Instagram account resets its cursor. Poll responses from before a connection change are discarded without advancing the cursor or marking a replacement token rejected. The recent-message limit and unverified equality of poll ids and webhook `mid`s remain. These changes are covered by local regression tests; absent real Meta deliveries remain an open external diagnosis.
